# Data Model: Async Command Processing

## Entity: Command

Represents a unit of asynchronous work submitted by an external system.

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| `id` | UUID/string | Yes | Unique command identifier returned as `command_id` | Generated by `SubmitCommand`; unique per accepted command |
| `type` | string | Yes | Command type used for handler registry lookup | Non-empty after trimming whitespace |
| `payload` | object | Yes | Command-specific payload | Must be an object at API boundary; type-specific validation occurs in the pipeline |
| `status` | CommandStatus | Yes | Current lifecycle state | One of `queued`, `processing`, `completed`, `failed` |
| `created_at` | datetime | Yes | Time command was accepted and recorded | Set when command is created |
| `started_at` | datetime | No | Time worker began processing | Set when status changes to `processing` |
| `completed_at` | datetime | No | Time worker finished processing attempt | Set when status becomes `completed` or `failed` |
| `error_message` | string | No | Safe failure summary | Set only for failed commands; must not expose sensitive payload details |

## Entity: CommandStatus

Allowed command lifecycle values:

- `queued`: accepted, recorded, and queued for asynchronous processing.
- `processing`: consumed by a worker and currently executing.
- `completed`: pipeline completed successfully.
- `failed`: pipeline failed, payload validation blocked processing, or no pipeline was registered for the command type.

## Entity: CommandContext

Shared context passed through Chain of Responsibility handlers.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `command` | Command | Yes | Command currently being processed |
| `metadata` | object/map | Yes | Mutable per-processing metadata shared by handlers |
| `errors` | list[string] | Yes | Handler-reported validation or processing errors |
| `result` | object/map/null | No | Optional command-specific result data |

## Ports and Application Contracts

- **CommandQueue**: publishes command identifiers and consumes queued command identifiers. Implemented by `RedisCommandQueue`.
- **CommandRepository**: saves commands, retrieves by id, and persists lifecycle updates. Implemented initially by `MemoryCommandRepository`.
- **CommandHandler**: receives `CommandContext`, performs one responsibility, and may add errors to stop the pipeline.
- **CommandPipeline**: executes ordered handlers for a command type.
- **HandlerRegistry**: maps `type` values to `CommandPipeline` instances and raises a controlled error for unknown types.

## State Transitions

```text
queued -> processing -> completed
queued -> processing -> failed
queued -> failed      # allowed when a worker cannot resolve a pipeline before execution
```

Rules:

- `SubmitCommand` creates commands only in `queued`.
- `ProcessCommand` sets `processing` before pipeline execution.
- Successful pipeline execution sets `completed`.
- Missing pipeline, payload validation interruption, or unexpected handler error sets `failed`.
- `completed_at` is recorded for both `completed` and `failed`.

## Initial Command Types

- `TEST_COMMAND`: implemented in v1 with a dedicated pipeline.
- `SEND_EMAIL`: documented as future extension example.
- `GENERATE_REPORT`: documented as future extension example.
